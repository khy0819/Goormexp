상세 해설

Q1. ESLint와 Prettier의 역할 차이로 올바른 것은?

정답 ESLint는 사용 안 하는 변수, useEffect 의존성 누락 등 코드의 논리적 문제를 잡아주고, Prettier는 들여쓰기·따옴표·세미콜론 같은 코드 스타일을 통일한다.

ESLint는 코드 퀄리티(Linter)를 담당하며, Prettier는 코드 포맷팅(Formatter)을 전담한다.

Q2. ESLint 9 버전에서 도입된 Flat Config의 특징으로 올바른 것은?

정답 배열 형태로 설정 객체를 나열하며, 배열의 뒤에 오는 설정이 앞의 설정을 덮어쓴다.

Flat Config(eslint.config.js)는 기존의 복잡한 extends 구조를 버리고 직관적인 배열의 Cascading(덮어쓰기) 방식을 채택했다.

Q3. ESLint 규칙 레벨 중 'warn'에 대한 설명으로 올바른 것은?

정답 에디터에서 노란 물결선이 표시되지만 빌드는 성공하며, 나중에 고칠 수 있다는 신호로 쓰인다.

'error'는 빨간 줄과 함께 CI/CD나 로컬 빌드를 실패하게 만들지만, 'warn'은 경고만 할 뿐 실행과 빌드를 막지 않는다.

Q4. no-explicit-any 규칙을 'error' 대신 'warn'으로 설정하는 이유로 올바른 것은?

정답 외부 라이브러리 타입 미지원이나 레거시 코드 마이그레이션 중 any를 써야 하는 경우가 있어 완전히 금지하면 개발이 어려워지기 때문이다.

현실적으로 타입 정의가 없는 서드파티 라이브러리를 사용할 때가 있으므로 유연성을 위해 warn으로 두는 경우가 많다.

Q5. eslint-config-prettier를 ESLint Flat Config 배열의 맨 마지막에 추가해야 하는 이유로 올바른 것은?

정답 ESLint의 포맷팅 관련 규칙들을 꺼서 Prettier와의 충돌을 방지하며, 나중에 오는 설정이 앞 설정을 덮어써야 이전 포맷 규칙들을 모두 비활성화할 수 있기 때문이다.

Flat Config는 배열의 뒤쪽 설정이 우선권을 가지므로, 마지막에 배치해야 기존 규칙 중 포맷팅 관련 규칙을 확실하게 끌 수 있다.

Q6. Prettier 설정에서 trailingComma를 사용하면 Git 관점에서 어떤 장점이 있는가?

정답 배열이나 객체에 항목을 추가할 때 기존 마지막 항목 줄은 변경되지 않고 새 줄만 추가된 것으로 Git diff에 나타나 diff가 깔끔해진다.

마지막 쉼표가 없으면 새 항목을 추가할 때 기존 줄(쉼표 추가)과 새 줄, 총 2줄이 변경된 것으로 인식되어 코드 리뷰가 불편해진다.

Q7. Husky의 pre-commit Hook과 lint-staged가 함께 동작하는 방식으로 올바른 것은?

정답 git commit 명령어를 실행하면 커밋 전에 자동으로 lint-staged가 실행되며, 에러가 있으면 커밋이 중단된다.

Husky가 커밋 액션을 가로채고 lint-staged를 실행시켜 퀄리티 게이트 역할을 수행한다.

Q8. package.json의 "prepare": "husky" 스크립트가 중요한 이유로 올바른 것은?

정답 npm install 실행 시 자동으로 실행되는 스크립트여서, 팀원이 프로젝트를 클론 받고 npm install만 해도 Husky가 자동으로 설치되기 때문이다.

prepare 스크립트는 패키지 설치 완료 후 자동으로 트리거되어, 모든 팀원의 로컬 환경에 Git Hook을 강제 적용할 수 있다.

Q9. lint-staged를 사용하는 주된 이유로 올바른 것은?

정답 git add로 스테이징된 파일만 검사하여 전체 파일 검사보다 빠르며, 이번 커밋에서 변경한 파일만 대상으로 검사할 수 있기 때문이다.

프로젝트가 커질수록 전체 파일을 린팅하는 것은 비효율적이므로, 변경된 파일만 타겟팅하여 속도를 높인다.

Q10. 소규모 스타트업 팀에서 Git Flow 대신 GitHub Flow를 선호하는 이유로 올바른 것은?

정답 GitHub Flow는 main과 feature 브랜치만 사용하는 단순한 구조로 빠르게 개발하는 소규모 팀에 적합하기 때문이다.

Git Flow는 브랜치가 많고 복잡하여 릴리즈 주기가 긴 대형 프로젝트에 적합하고, 빠른 배포가 필요한 스타트업은 가벼운 GitHub Flow를 선호한다.

Q11. Conventional Commits 규칙에 따른 커밋 메시지 형태로 올바른 것은?

정답 feat(auth): 로그인 기능 구현

타입(스코프): 제목 형태를 지키는 것이 규칙이다. (예: feat, fix, chore, refactor 등)

Q12. 코드 리뷰에서 "nit:" 접두어를 사용하는 의미와 목적으로 올바른 것은?

정답 리뷰어의 취향이나 선호에 따른 선택 사항이며, 반영 여부는 리뷰이가 자기 판단으로 결정해도 된다는 의미이다.

Nitpick의 줄임말로, 사소한 제안이나 스타일 관련 의견을 낼 때 사용하여 리뷰이의 부담을 줄여주는 좋은 커뮤니케이션 스킬이다.

Q13. 기존 코드베이스가 있는 팀에 ESLint를 처음 도입할 때 규칙을 'error' 대신 'warn'으로 시작하도록 권장하는 이유는?

정답 규칙을 바로 error로 설정하면 기존 코드에서 에러가 대량으로 발생하여 빌드 자체가 불가능해질 수 있기 때문이다.

점진적 도입을 위해 처음에는 warn으로 설정하여 가시성만 확보하고, 점차 수정해나가면서 error로 격상시키는 것이 바람직하다.

Q14. .vscode/settings.json 파일을 Git에 커밋해야 하는 이유로 올바른 것은?

정답 팀원이 프로젝트를 클론 받고 VS Code로 열면 저장 시 자동 포맷팅 등 동일한 에디터 설정이 자동으로 적용되어 팀원마다 따로 설정하지 않아도 되기 때문이다.

팀 레벨의 확장 프로그램 설정 및 포맷터(Format on Save) 세팅을 공유하여 휴먼 에러를 방지합니다.

Q15. 프론트엔드 개발자가 백엔드와 협업 시작 전에 미리 협의해야 할 내용으로(통상적으로) 옳지 않은 것은?

정답 프론트엔드 코드의 컴포넌트 파일 구조와 폴더 네이밍 컨벤션

폴더 구조와 컴포넌트 네이밍은 프론트엔드 내부의 규칙이므로 백엔드 개발자와 협의할 API 응답이나 인증 방식과는 무관하다.
