상세 해설

Q1. CI(Continuous Integration)와 CD(Continuous Deployment)의 역할로 올바른 것은?

정답 CI는 push나 PR 시 자동으로 빌드와 테스트를 실행하여 프로덕션 가기 전 문제를 잡고, CD는 CI를 통과하면 자동으로 서버에 배포한다

CI는 코드 병합 전 빌드 및 테스트를 자동화하여 품질을 유지하고, CD는 안전성이 검증된 코드를 서버에 자동 배포하는 파이프라인 역할을 한다.

Q2. 다음과 같이 워크플로우를 구성했을 때, lint, test, build의 실행 방식으로 올바른 것은? (needs: [lint, test])

정답 lint와 test는 병렬로 실행되고, 둘 다 성공해야 build가 실행된다

GitHub Actions에서 Job은 기본적으로 병렬로 실행되지만, `needs` 키워드를 사용하면 지정된 Job이 성공적으로 완료된 후에만 실행되도록 순서를 제어할 수 있다.

Q3. CI 환경에서 npm install 대신 npm ci를 사용해야 하는 이유로 올바른 것은?

정답 npm ci는 package-lock.json에 지정된 정확한 버전을 설치하여 재현 가능한 빌드를 보장하고, npm install은 설치 시점에 따라 버전이 달라질 수 있기 때문이다.

`npm ci`는 의존성 버전 충돌을 막고 항상 동일한 환경을 구축하기 위해 `package-lock.json`을 기준으로 클린 설치(Clean Install)를 진행한다.

Q4. CI 워크플로우에서 Vitest를 실행할 때 npm run test -- --run과 같이 --run 옵션을 반드시 붙여야 하는 이유는?

정답 Vitest의 기본 실행 모드가 watch 모드여서 --run 없이는 파일 변경을 기다리며 워크플로우가 영원히 종료되지 않기 때문이다.

CI 파이프라인은 작업을 끝내고 성공/실패 여부를 반환해야 하므로, 코드를 감시하며 무한 대기하는 watch 모드를 끄는 `--run` 옵션이 필수적이다.

Q5. GitHub Actions에서 Job과 Step의 차이로 올바른 것은?

정답 Job은 워크플로우 안에서 독립적인 작업 단위로 기본적으로 병렬 실행되고, Step은 하나의 Job 안에서 순서대로 실행되는 개별 명령이다.

워크플로우는 여러 Job으로 나뉘며 서로 간섭 없이 병렬 실행된다. 반면 특정 Job 내부의 Step들은 정의된 순서에 따라 위에서 아래로 순차 실행된다.

Q6. Vite 프로젝트에서 클라이언트 코드가 환경 변수에 접근할 수 있는 조건으로 올바른 것은?

정답 변수 이름에 VITE_ 접두사가 있어야 클라이언트 코드에서 접근 가능하며, 접두사가 없는 변수는 빌드 시 클라이언트 코드에서 제거된다.

Vite는 보안(중요한 DB 암호 등 노출 방지)을 위해 `VITE_`라는 명시적인 접두사가 붙은 환경 변수만 클라이언트 측 번들에 포함시킨다.

Q7. Vite 프로젝트에서 환경 변수에 접근하는 방법과 그 특성으로 올바른 것은?

정답 import.meta.env.VITE_API_URL로 접근하며, 빌드 시점에 해당 값이 JS 파일에 박혀 런타임에 변경이 불가능하다.

CRA의 `process.env`와 달리 Vite는 `import.meta.env`를 사용한다. 프론트엔드 환경 변수는 빌드 타임에 정적 문자열로 치환되므로 배포 후 동적 변경이 불가하다.

Q8. Vite 환경 변수의 동작으로 올바른 것은?

정답 빌드 시 값이 주입되므로 값 변경 후에는 재빌드/재배포가 필요할 수 있다

환경 변수 값이 변경되었다면, 이전 값으로 하드코딩되어 번들링된 결과물을 버리고 다시 빌드해야 새로운 값이 반영된다.

Q9. GitHub Secrets의 보안 특성으로 강의에서 언급된 내용과 일치하는 것은?

정답 워크플로우 실행 중 로그에 출력되면 ***로 마스킹되고, 한 번 설정하면 값을 다시 볼 수 없으며 재설정만 가능하다

Secrets는 깃허브 서버에 안전하게 보관되며, 설정 후에는 관리자라도 평문(Plain text)을 다시 읽을 수 없도록 설계되어 있다.

Q10. Vercel만 사용할 때와 GitHub Actions를 함께 사용할 때의 차이로 올바른 것은?

정답 Vercel은 빌드 성공 여부만 확인하므로 테스트가 실패해도 배포되지만, GitHub Actions를 함께 사용하면 lint, type check, test 통과까지 검사하여 코드 품질을 보장한다.

Vercel의 기본 CI는 빌드 단계에서만 오류를 잡는다. 세밀한 품질 검증(Linting, Unit Test 등) 파이프라인을 추가하려면 Actions 연동이 필요하다.

Q11. React Router를 사용하는 SPA를 Vercel에 배포했을 때 /products/123 URL을 새로고침하거나 직접 입력하면 404가 발생하는 이유와 해결책으로 올바른 것은?

정답 서버가 /products/123이라는 파일을 찾지 못해 404를 반환하기 때문이며, vercel.json에 모든 요청을 index.html로 보내는 rewrites를 설정하면 해결된다

SPA 라우팅은 클라이언트 자바스크립트가 담당한다. 서버 측에는 해당 경로의 HTML이 없으므로, 알 수 없는 요청은 모두 `index.html`로 폴백(Fallback) 처리해야 한다.

Q12. Vercel의 Preview 배포에 대한 설명으로 올바른 것은?

정답 PR을 생성하면 해당 PR에만 해당하는 고유 URL이 자동으로 생성되어 PR 코멘트에 달린다

Vercel은 PR 생성 시 프로덕션 환경과 똑같이 동작하는 임시 배포 환경(Preview)을 제공하여, 코드를 병합하기 전에 실제 동작을 브라우저에서 테스트할 수 있게 해준다.

Q13. GitHub Actions에서 actions/setup-node의 cache: 'npm' 설정이 어떻게 캐싱을 처리하는지로 올바른 것은?

정답 package-lock.json의 해시값을 기반으로 npm 캐시 디렉터리(~/.npm)를 재사용해, lock 파일이 바뀌지 않으면 설치 시간을 단축한다.

매 빌드마다 패키지를 전부 다시 다운로드하는 것을 막기 위해, 의존성에 변화가 없을 경우 기존 캐시를 불러와 파이프라인 속도를 최적화한다.

Q14. GitHub의 Branch Protection Rules에서 'Require status checks to pass before merging'을 설정하는 효과로 올바른 것은?

정답 지정한 status check가 통과하지 않으면 Merge 버튼이 비활성화되어 테스트 실패 코드가 main 브랜치에 병합되는 것을 막는다

보호된 브랜치에 코드를 병합하기 전, GitHub Actions 등에서 정의한 필수 테스트나 린트 검사가 통과하도록 강제하는 안전장치이다.

Q15. GitHub Actions 워크플로우에서 paths-ignore: ['**.md'] 설정의 목적으로 올바른 것은?

정답 README.md 같은 마크다운 파일만 변경됐을 때는 CI 워크플로우를 실행하지 않아 불필요한 실행 낭비를 방지하기 위해서다.

코드 로직과 무관한 단순 문서 수정 커밋에서 Actions가 트리거되는 것을 막아 컴퓨팅 리소스와 실행 비용을 절약할 수 있다.
